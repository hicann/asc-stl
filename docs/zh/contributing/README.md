# 贡献指南

API参考页面的结构、术语、示例和导航要求见
[ASC-STL API文档编写规范](api_writing_guidelines.md)。

感谢你对ASC-STL的关注。本章介绍贡献者常用的问题讨论、开发、测试、PR和审核流程。

## 开始之前

ASC-STL接受功能开发、缺陷修复、性能优化、测试和文档贡献。提交改动前，请阅读项目行为准则并按项目要求签署CLA。

除简单缺陷修复外，新增功能、头文件、API、重载、配置项或运行环境前，应先通过Issue说明使用场景和方案。

## 准备改动

| 场景 | 提交前准备 |
| --- | --- |
| 缺陷修复 | 提供最小复现、预期行为、实际行为和环境信息 |
| 新功能或API | 说明使用场景、接口方案、适用范围与限制、兼容性和测试计划 |
| 性能优化 | 提供优化前基线、测试环境、数据规模、性能对比和正确性结果 |
| 文档修订 | 指出原文位置、问题、修改依据及相关代码影响 |

安全问题不得在公开Issue中提交密钥、凭据、内网地址或完整私有日志，请按照项目安全流程报告。

## 开发流程

1. 创建或认领Issue，确认问题和改动范围。
2. 同步目标分支，并创建只服务于一个改动目的的开发分支。
3. 同步更新代码、测试和受影响的文档。
4. 运行全部适用的本地检查，并记录环境、命令和结果。
5. 提交PR，说明背景、目的、方案、关联Issue、测试结果和文档变化。
6. 根据审核意见修改，并由CI验证PR的最终内容。

## 构建与测试

- 产品代码使用C++17基线，头文件必须能够单独包含。
- 新增接口必须说明适用环境、输入输出、资源所有权、错误处理和接口行为。
- 缺陷修复应增加回归测试；新功能应覆盖正常、边界和错误场景。
- 测试预期结果应由独立方法计算或人工确认，不得调用被测API自身生成。
- 公共接口行为变化时，代码、测试、API说明和发布说明必须同步更新。
- Device原子、同步、GM/UB、集体操作、浮点运算和并行算法改动应补充Ascend 950 AI Core测试。

## 创建Pull Request

PR至少应包含：

1. 业务背景、问题描述和关联Issue。
2. 方案和用户可见影响。
3. 修改范围及新增或调整的API。
4. Host、Device和仿真测试结果。
5. 文档更新、已知限制和未覆盖风险。
6. 性能改动的基线与对比结果。

## 审核与合入

PR通过全部相关CI检查，并完成必要的验证、文档更新和审核意见处理后，方可合入。PR新增提交后，应重新执行或确认相关测试。
